# 開発ワークフロー

エージェントと人間が同じリズムで進むための標準プロセス。

## 全体像

```text
問題定義
  → MECE 分解 + 評価軸付き比較
  → ADR（採用案の決定）
  → 深い Module / Seam 設計
  → TDD（Red → Green × N）
  → レビュー / 必要なら RCA
```

認知リズム: **問いを狭める → 決める → 小さく作る → 確かめる**。同じターンで「広く調査」と「広く実装」を混ぜない。

## フェーズ別ゲート

### 1. 調査・解析

- [ ] 問いが 1 文で言える
- [ ] MECE な分解（漏れ・重複なし）
- [ ] 評価軸と各軸の判定基準がある
- [ ] 「実トレンド vs 代替」などドメイン禁忌を踏まえている

→ skill: `mece-analysis`

### 2. 設計判断

- [ ] 選択肢が 2 つ以上
- [ ] トレードオフが軸で比較されている
- [ ] `docs/adr/NNNN-*.md` に記録（Status: Proposed → Accepted）

→ skill: `adr`

### 3. モジュール設計

- [ ] 公開 Interface が小さい（深い Module）
- [ ] テストする Seam が合意されている
- [ ] 一度に扱う関心を 1〜2 に抑えている

→ skill: `cognitive-design`

### 4. 実装（TDD）

- [ ] 失敗するテストが先（Red）
- [ ] 通す最小実装（Green）
- [ ] 1 cycle = 1 振る舞い
- [ ] リファクタはレビュー段階（ループに混ぜない）

→ skill: `tdd`

### 5. 障害対応

- [ ] 再現ループがある（Red 可能なコマンド）
- [ ] なぜなぜで因果を掘る（症状で止めない）
- [ ] 修正後に回帰テストが残る

→ skill: `root-cause-analysis`

## セッションの始め方（推奨プロンプト）

- 「`docs/workflow.md` に従い、まず問いを定義して MECE で比較して」
- 「この ADR を Accepted にしてから TDD で実装して」
- 「落ちている原因を RCA skill で診断して」
